# Level Authoring And World Editor Design

## Purpose

This design separates fine room construction from coarse world layout. A creator inherits a reusable room template to author tiles, entities, and presentation. A minimal Godot `EditorPlugin` places completed rooms on a 320x180 chunk grid and defines directed room connections. Runtime scenes and resources are generated by an explicit bake step.

The existing authored tile placement in `scenes/game.tscn` remains untouched until the creator manually migrates it in the Godot editor. `docs/todo.md` is reference material and is not modified by this work.

## Concepts And Ownership

### Chunk

A chunk is a fixed 320x180-pixel world-layout unit. World-editor movement always changes an integer `Vector2i` chunk coordinate. Pixel origin is calculated as:

```gdscript
room_origin_pixels = room_origin_chunk * Vector2i(320, 180)
```

### Room

A room is one rectangular group of one or more chunks. The smallest room is one chunk. Its source scene owns its size and content; the world owns its placement. A room ID may occur only once in a world.

Room overlap is permitted so intentional overlays remain possible, but validation and the editor canvas must report it as a warning.

### Authoring Source

`scenes/templates/level_template.tscn` is the inheritance source. A concrete level such as `scenes/levels/level_0.tscn` inherits it. The expected contract is:

```text
RoomAuthoringRoot
|-- RoomPreviewController
|-- RoomContent
|   |-- Background
|   |-- Terrain
|   |   |-- BackTiles
|   |   |-- SolidTiles
|   |   |-- GlassTiles
|   |   |-- VisionBlockTiles
|   |   |-- DetailTiles
|   |   `-- MarkerTiles
|   |-- Entities
|   `-- Foreground
`-- PreviewOnly
    |-- Player
    |-- PixelCamera2D
    |-- FogOfWar
    |-- GridOverlay
    `-- DebugHud
```

The root exports `room_id`, `display_name`, `room_size_chunks`, `preview_spawn_id`, `map_color`, and `tags`. `RoomPreviewController` initializes direct play and binds preview persistence in memory. `room_origin_chunk` is deliberately absent because it belongs to world layout.

`RoomContent` is bakeable. `PreviewOnly` exists only for direct room play and is excluded from generated assets. Direct preview never writes a real save slot, and exits cannot transfer to another room.

### World Layout

`WorldData` owns world membership, room origins, the start room/spawn, and directed `RoomConnectionData` entries. An authoring scene owns entrance and spawn IDs but not their destinations. `RoomConnectionData` is the only runtime authority for resolving `from_room_id + from_entrance_id` to `to_room_id + to_spawn_id`.

## Generated Assets

For `level_0`, room baking produces:

```text
scenes/rooms/generated/level_0_runtime.tscn
scenes/rooms/generated/level_0_terrain.tscn
resources/rooms/generated/level_0_room.tres
```

The runtime scene contains non-terrain `RoomContent`, including entities, foreground, and creator nodes. The terrain scene contains the six semantic `TileMapLayer` nodes plus static background nodes. `RoomData.scene_path` points to runtime content, while new `source_scene_path` and `terrain_scene_path` fields preserve provenance and terrain loading.

Terrain scenes remain separate per room and are positioned at exact pixel origins under a persistent `TerrainRoot`. They are not merged into one global cell grid: 180 pixels is not divisible by the 8-pixel tile size, so a merged grid would introduce vertical drift. Runtime room content uses the same exact pixel origin.

Generated paths are deterministic. Baking stages all outputs first, validates them, then replaces prior generated files. Failed validation leaves the last valid output intact.

## Minimal World Editor

> **Superseded UI:** This side-dock design is retained as historical context. The active
> center-workspace design is `docs/superpowers/specs/2026-09-06-world-editor-main-screen-redesign.md`,
> implemented by `docs/superpowers/plans/2026-09-06-world-editor-main-screen-redesign.md`.

The plugin lives under `addons/wellwell_world_editor/` and provides a dock with one layout canvas and a compact toolbar:

- Create a room scene inherited from the template.
- Add an existing authoring room to the current world.
- Remove only the world reference; never delete source or generated files.
- Drag a room by whole 320x180 chunks.
- Show room bounds, ID/name, directed connections, start room, and overlap warnings.
- Select a source entrance and target spawn to create or remove a connection.
- Open the selected room source scene.
- Validate or bake the selected room, then validate or bake the world.
- Record mutating operations with `EditorUndoRedoManager`.

The plugin does not edit tiles, entities, room dimensions, rendering settings, or arbitrary scene nodes. It has no automatic layout, rotation, nested worlds, multi-selection, copy/paste, or source-file deletion.

## Runtime Composition

`WorldSession` coordinates one persistent player, camera, fog instance, debug HUD, `TerrainRoot`, and `WorldRuntime`:

1. Load every generated terrain scene once because tile-only rooms are inexpensive.
2. Resolve the saved or configured start room and spawn.
3. Load runtime content for the current room and the spatial/connected neighbor set.
4. Bind the persistent player to camera, fog, HUD, and world runtime through explicit methods.
5. Emit readiness only after the target room and spawn exist; the menu may hide after that signal.

Residency is based on rooms occupying the player's current chunk and four orthogonal neighboring chunks, plus rooms directly connected to the current room. Transitions stage required rooms before unloading obsolete ones. A load failure preserves the previous playable state.

Fog remains room-local. On room change it receives that room's chunk rectangle and terrain blockers. Visibility is flood-fill propagation from the player's cell: solid and vision-blocking cells stop expansion, glass is visible but stops expansion beyond itself, and ordinary cells propagate. The mask texture updates every frame for post-processing.

## Validation

Hard errors block baking:

- Missing or duplicate room IDs, entrance IDs, spawn IDs, or entity IDs.
- Non-positive room size or missing required authoring nodes/layers.
- Missing source/runtime/terrain paths.
- Connections whose source entrance or target spawn does not exist.
- Invalid start room or start spawn.
- Runtime content containing `PreviewOnly` nodes.

Warnings do not block baking:

- Overlapping room rectangles.
- Unconnected entrances.
- Rooms unreachable from the start room.
- Marker tiles outside declared room bounds.

## Manual Godot Checkpoints

The creator performs editor-dependent work: create the inherited `level_0` scene, move the existing tile layers/content without changing tile placement, enable and visually inspect the plugin, and run a final playthrough. Automated work supplies scripts, resources, tests, validation, and generated-output contracts; it does not simulate visual approval.

## Acceptance Criteria

- A room can run alone without modifying actual saves.
- A world can add, remove, move, connect, validate, and bake rooms from the dock.
- Room movement is integer-chunk-only and preserves exact 320x180 pixel spacing.
- Generated terrain stays resident while non-terrain room content streams transactionally.
- Connections resolve only through `WorldData`.
- Fog consumes the active room's blockers and exposes a current per-frame mask texture.
- Existing `game.tscn` tile placement and `docs/todo.md` are unchanged.
